Automatic WhatsApp greeting after a scan

What happens

When a scanned card is saved, the new contact receives: "Hello {name}, nice to meet you today. This is an automated message from my AI agent." then "Here is my business card." with an image of the sender's card attached.

How it is built

Saving the contact triggers an Odoo automation rule ("after creation") that sends an approved WhatsApp template with the card image as its attachment. Odoo's automation rules include a "Send WhatsApp" action, which needs a template to exist.

Conditions

What Meta requires

  • A WhatsApp Business account and number for MOL; the message comes from that number, not a personal WhatsApp.
  • A business may only start a conversation with a message template approved in advance.
  • The person must have opted in to be messaged; the app should record that at the scan.
  • Templates are charged per message by Meta.

Sources: Meta: Get opt-in for WhatsApp[9] · WhatsApp Business messaging policy[10] · Odoo: automation rules[11] · Odoo forum: automating a WhatsApp template[12]. The original wording asked for was "nice to meet you on today. This an automated message by my AI agent"; grammar is corrected above and can be set to any approved wording.

Japanese character recognition

Google's ML Kit Text Recognition v2 has a separate on-device recogniser for Japanese, covering kanji, hiragana and katakana, alongside the Latin one. The app bundles both and runs them on each card, so bilingual cards are read in one pass. The open-source card reader listed above ships with the Latin recogniser only, so the Japanese one is an addition we make. Accuracy on vertical text and decorative fonts must be tested on real MOL cards.

Research · vehicle monitoring

ESP32-based OBD devices that send data to the cloud

The question: can a small device in each vehicle's diagnostic port tell Odoo how long the engine was moving, idling or off?

What the device must read

Two standard OBD-II values are enough: engine speed (RPM) and vehicle speed. Engine running with speed at zero is idling. Engine run time, fuel level and odometer are useful extras where the vehicle provides them.

Why ESP32

The ESP32 is a low-cost microcontroller with Wi-Fi and Bluetooth built in and a CAN interface for talking to the vehicle. It is programmable, so the firmware can be written to send only what MOL allows.

Why add it to the tablet

The tablet estimates engine state from vibration. An OBD device reads engine speed directly, so idling is measured, not inferred. The two can run together: GPS from the tablet, engine data from the port.

First step: use the vehicle tablet as the sensor

A tablet fixed in each vehicle was already suggested for attendance. The same tablet carries a motion sensor and GPS, which give GPS position, trips, and moving, idling and parked time with no device in the car's diagnostic port.

Signal from the tabletWhat it tells usLimit
GPS speedPosition and speed. Above walking pace, the vehicle is moving; at zero, it is standing. Positions over time give each trip.Weak signal in basement car parks and between tall buildings
Vibration (accelerometer)A running engine shakes the cabin in a steady pattern. Standing with that pattern is idling; standing without it is parked.Needs tuning per vehicle model and a rigid mount; a quiet engine is harder to detect
Charging stateIf the tablet is powered from a socket that is live only with the ignition on, "charging" means the ignition is on.Depends on how each vehicle's socket is wired
How it classifies

Three states

  • Moving: GPS speed above a threshold.
  • Idling: speed zero, with engine vibration or ignition power.
  • Parked: speed zero, no vibration, no ignition power.
What is sent

GPS, movement and state

The tablet sends GPS position, speed and vibration readings to Odoo at intervals. Odoo keeps the trips and the time spent in each state, for example "idling, 14 minutes, Ayala Avenue".

Honest limits

An approximation

  • It estimates engine state; it does not read it.
  • Hybrid vehicles stop their engine at standstill, so "on but silent" looks like parked unless ignition power is used.
  • It needs a small Android app, which TechNext would build.
  • Accuracy should be checked against a manual log during a trial.

Basis: a 2014 journal paper describes separating moving, idling and engine-off states from accelerometer vibration alone, and several patents describe combining accelerometer and GPS on a handheld device for the same purpose (paper[18], patent US 9,646,427[19], patent US 10,019,762[20]). We found no published accuracy figures for tablets in these vehicle models. If the trial shows the estimate is not accurate enough, the OBD devices below read the engine directly.

Compatibility with MOL's vehicles

Short answer: neither maker lists any of MOL's five models, and we found no owner report confirming either device on them. Both devices speak the protocols these vehicles use, so the limit is what each car chooses to expose, not the device. That can only be settled by plugging in.

MeatPi WiCAN Pro

What the maker states

  • Protocols: CAN (ISO 15765-4, 11-bit and 29-bit), J1939, raw CAN, KWP2000 (ISO 14230-4) and J1850.
  • Reads standard OBD-II values on any vehicle that provides them; the maker warns that some manufacturers switch certain standard values off.
  • Published vehicle list is user-submitted. Toyota entries: Hilux, RAV4, bZ4X. No Alphard, Innova or Zenix. No Isuzu. Mitsubishi entries are electric and plug-in models only.
  • Has a built-in "scan standard PIDs" function, which makes the plug-in test quick.
  • An unlisted model can still work on standard values; a model profile can be requested or written.
Freematics ONE+ (Model B)

What the maker states

  • Protocols: CAN at 500 and 250 kbps, 11-bit and 29-bit, and KWP2000 (fast and 5-baud). Model B also lists J1939.
  • No vehicle compatibility list is published.
  • Reads standard OBD-II values through its own firmware library; anything else needs custom code.
  • One user reported it did not work on a Renault, so failures on individual models do occur.
  • 4G is built in, so it does not depend on a tablet hotspot.

What this means

Good enough for idle detection, probably

Idle detection needs only engine speed and road speed, the two most basic values. Those are the most likely to be available on all five. Fuel rate and fuel level are much less certain.

Cheapest check

A ten-minute test per vehicle

Before buying either device, plug a basic OBD reader into each vehicle with a phone app and note whether engine speed and road speed appear. If they do, both devices should read them too.

Need from MOL

Model year and engine

The year and engine of each vehicle decide the answer, especially for the Alphard and Zenix. Philippine-market vehicles are not bound by the US and EU rules that guarantee these values, which is why testing matters.

"Likely" and "uncertain" are our judgement from these sources, not test results.

Risks

What could stop it working

  • Toyota access limits. Newer Toyotas have a security gateway. Standard readings such as RPM and speed are the most likely to remain available, but we found no confirmation for the Alphard, Innova or Zenix. This must be tested on the actual vehicles.
  • Diesel models. The mu-X and Montero may expose fewer standard values. Also to be tested.
  • Battery drain. The device draws power from the port; it must sleep when the engine is off.
  • Warranty and dealer view. Check with the dealers before leaving a device plugged in.
  • Security review. The device, its firmware and the cloud receiver are a new system for the Tokyo assessment.
Recommendation

Pilot before purchase

  • Start with the tablet method above; it needs no vehicle hardware.
  • In parallel, buy two off-the-shelf ESP32 units (WiCAN Pro and Freematics ONE+).
  • Test on one vehicle of each model for two weeks.
  • Record which values each vehicle exposes and whether idle minutes match a manual log.
  • Send engine state alongside the tablet's GPS data.
  • Decide then between an off-the-shelf unit and a custom build.
  • Fallback if a model blocks the port: the tablet estimate plus daily odometer photos and Shell fuel data.

Preparation · fuel tracking

Shell fuel card data by email, read by an AI agent

MOL computes fuel use from Shell fleet card data today, and told us the export has discrepancies and empty fields. This is the workflow we propose in place of the manual work.

1 · Send

Staff download the statement or transaction export from the Shell fleet card portal[48], or forward the email Shell sends, to an address such as fuel@ on MOL's Odoo. Any format Shell provides is accepted: Excel, CSV or PDF.

2 · Extract

The agent reads each transaction: date and time, card number, vehicle or driver named on the card, product, litres, amount, station, and the odometer keyed in at the pump, where there is one.

3 · Interpret

It matches cards to vehicles, estimates missing odometer readings from neighbouring fills and the drivers' daily readings, computes kilometres per litre, and flags values that cannot be right.

4 · Reply

It answers the same email with a summary: what was filed as read, what was estimated and why, and what it held back for a person to decide.

5 · File

Each fill-up becomes a fuel service record on the vehicle in Odoo Fleet, with litres, cost and odometer. Estimated values carry an "estimated" mark.

6 · Correct

Staff reply to the email with a correction, or edit the record in Odoo. Confirmed values are never overwritten by a later estimate.

Risks

What needs care

  • Wrong guesses. An estimate can be wrong. Marking every estimate, and holding back doubtful rows, keeps errors visible.
  • Data security. The statement holds card numbers, plates and spending. The agent must run inside Odoo or MOL's Microsoft tenant, or pass MOL's AI assessment.
  • Format changes. If Shell changes its export layout, the agent adapts better than a fixed import, but the first files should be checked by hand.
  • Not real time. Data arrives when someone forwards it. A weekly routine is enough for cost reporting.
To confirm with MOL

Before it is built

  • A sample Shell export, to see its columns and the empty fields MOL mentioned.
  • How cards are assigned: one per vehicle, or one per driver.
  • Who forwards the file, and how often.
  • Whether MOL prefers the agent inside Odoo or in its Microsoft environment.

The Shell portal's export formats and fields are assumed from MOL's description in the discovery session; we have not seen a sample file. The agent itself is a custom build on Odoo's incoming-mail and automation features.

Preparation · driver attendance

Clock-in with odometer photo and location

The flow

Start and end of day, in the Odoo app: clock in or out with location on, photograph the odometer, type the reading. The reading posts to the vehicle's odometer log in Fleet; the photo is kept as evidence.

What is standard, what is added

Odoo Attendances already supports mobile check-in and can record the location of each one. The odometer photo and reading, and the link from the attendance to the driver's vehicle, are additions we would build.

Points to settle

  • Location at clock-in and clock-out from the phone; continuous GPS where a tablet is fitted — to state in the driver policy
  • Personal or company phones for agency drivers
  • What happens with no signal: allow a late sync
  • Typed reading is checked against the last one; the photo settles disputes

Third-party examples of location-stamped attendance: v3c_hr_attendance[35], ps_geofencing_attendance[36]. One Odoo forum user reported inaccurate mobile locations on Odoo 17, so accuracy should be tested on the drivers' phones.

Research · office attendance

Connecting ZKTeco terminals to Odoo

Odoo has no official ZKTeco connector, and we found none maintained by the Odoo Community Association. Several third-party modules exist for current Odoo versions. They connect in one of two ways.

Preferred

Push (ADMS)

The terminal sends each punch to Odoo over the internet as it happens. Nothing needs to reach into the office network, which suits a cloud-hosted Odoo. The terminal's firmware must support ADMS.

Alternative

Pull (pyzk)

Odoo connects to the terminal on port 4370 and downloads the log on a schedule. Odoo and the terminal must be on the same network, or the port must be opened through the office firewall.

Manual route: email the attendance file to an AI mailbox

A fallback that works with any ZKTeco model and needs no network changes. It suits the period before a connector is approved, or terminals that cannot push.

What the administrator does

  • Exports the attendance log from the terminal or its desktop software, as it does today.
  • Emails the file to a dedicated address, for example once a day or once a week.
  • Reads the reply and fixes the few rows it flags.

What the parser does

  • Accepts the file as exported: text, CSV or Excel, whatever the column layout.
  • Matches each device user ID to an Odoo employee.
  • Pairs punches into check-in and check-out, skips rows already imported, and creates the attendance records.
  • Flags what it cannot resolve: unknown IDs, a missing clock-out, duplicate punches.
To settle

Before it is used

  • Attendance data is personal data, so the AI service is part of MOL's security assessment. It can run inside MOL's Microsoft tenant or inside Odoo to keep data in an already-assessed boundary.
  • Only approved sender addresses are accepted.
  • It is not real time: records arrive when the file is sent.
Recommendation

Email route first, push connector next

Start with the manual email route, which works on day one with any model. Then shortlist a push-capable module with reviewable code (DPS or Mindscript) and test it against MOL's actual terminals before committing. Vendor claims above are unverified.

Hosting decided

Odoo.sh

The project will be hosted on Odoo.sh. Unlike Odoo Online, it allows third-party and custom modules, so the ZKTeco connector, the email parser and the attendance additions can all be installed. Odoo.sh is billed by Odoo in addition to user licences.

Microsoft 365 E5: what MOL already has

MOL told us it uses Microsoft E5 licences and builds its custom apps on the Power Platform. This is what that licence gives, which AI is available in it, and how it bears on this project.

Included in E5

The main parts

  • Power Apps and Power Automate "for Microsoft 365"
